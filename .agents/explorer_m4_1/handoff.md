## 2. Logic Chain
- Since `AgentService` needs to coordinate the streaming process and return updates to the caller, it should return a stream of structured events (`AgentStreamEvent`) representing content, reasoning, search statuses, and generated database-ready messages.
- Since tool calling is streamed incrementally by the LLM, `AgentService` must use an accumulator to assemble the `arguments` and `id` of the tool call before executing the search.
- Once search completes, we need to inject the intermediate tool interaction history. Emitting a `ToolCallExecutedMessageEvent` containing the assistant message (with `tool_calls`) and the tool message (with `role: 'tool'`) allows the caller (e.g. Riverpod provider) to persist them in SQLite and update the UI.
- When `@search` prefix manual trigger is detected, the LLM is bypassed initially. The query is sent straight to `SearchService.search`. To ensure consistency in chat UI/DB, we simulate the assistant and tool messages as if the LLM called the tool automatically. Then we feed these simulated messages into the final LLM stream request.
- Since `SearchService` doesn't support `CancelToken` directly in its signature, checking `cancelToken.isCancelled` immediately before and after the async search execution resolves this constraint, ensuring immediate cancellation.
- Custom subclass mocking of `ChatService` and `SearchService` avoids brittle external packages and keeps tests clean and robust.

## 3. Caveats
- Checked `SearchService.search` signature which does not accept `CancelToken`. We assumed the query execution itself is fast enough that checking `cancelToken.isCancelled` before/after is sufficient to avoid starting subsequent calls.
- Assumed standard OpenAI-compliant streaming formats for tool calls, where `choices[0].delta.tool_calls` contains the incremented index and function arguments.
